# حالة SEC-OWNER-01 وخطوات الوصول إلى الدمج

آخر تحديث: 19 سبتمبر 2026

آخر Commit برمجي متحقق منه: `cf66ebe354986c1db03df3d4da57bfb9e1979cda`

## 1. ما تم تنفيذه

- فصل `SYSTEM_OWNER` بالكامل عن مستخدمي العميل وSetup وواجهات وصلاحيات `ADMIN`.
- إنشاء طلب Commissioning مرتبط بهوية التثبيت ولا يحتوي مفتاح الشركة الخاص.
- أداة Offline لتوقيع حزمة Ed25519 قصيرة العمر ومستخدمة مرة واحدة.
- ربط الحزمة بالتثبيت والعميل والموقع، ورفض العبث والانتهاء والتكرار والجهاز المختلف.
- إنشاء `SYSTEM_OWNER` منفردًا فقط بعد التحقق من التوقيع.
- إلغاء مسار Bootstrap المحلي القديم الذي كان يتجاوز حماية الشركة.
- MFA/TOTP إلزامي قبل منح جلسة Owner كاملة.
- قفل الحساب بعد 5 محاولات فاشلة لمدة 15 دقيقة.
- Rate Limit مستقل: 10 طلبات دخول لكل عنوان IP خلال دقيقة مع `429` و`Retry-After`.
- جلسات محفوظة ومنتهية الصلاحية وقابلة للإلغاء منفردة أو بالكامل.
- صلاحيات دعم مؤقتة محددة النطاق والمدة وقابلة للإلغاء فورًا.
- سجل تدقيق أمني مع منع تسجيل كلمات المرور وTOTP والـTokens والأسرار.
- منع `ADMIN` من تعداد أو إنشاء أو تعديل أو حذف أو انتحال Owner.
- Trust Keyring ثابت ومحمي، مع رفض المفتاح المجهول أو الملغي أو غير Ed25519.
- عقد بناء يفشل مغلقًا: Pilot يمنع Production keyring، وProduction يرفض البناء بدونه.
- توثيق حفظ المفتاح والتدوير والإلغاء والتعافي واستبدال جهاز العميل.

الأدلة التشغيلية المسجلة في جلسة القبول:

- GitHub Actions workflow `Internal Windows Setup` run ID `35132483885` اكتمل بنجاح.
- Artifact: `BIO-EMS-Setup-e48bba4168ee53393740125963cdc8ec278f4cff-bio-egypt-pilot-signed`.
- ملف التثبيت: `BIO-EMS-Setup-0.20.0-x64.exe`.

- التثبيت أنشأ بيانات Administrator أولية عشوائية في
  `C:\\ProgramData\\BIO-EMS\\config\\bootstrap-credentials.txt`؛ لا تُسجل كلمة المرور
  نفسها في التوثيق أو GitHub.
- تسجيل الدخول بالحساب `admin` ذي الدور `ADMIN` نجح فعليًا، وظهرت واجهة
  Administration / Users والحساب بحالة `active`.
- فحص قاعدة بيانات التثبيت بعد الاختبار أظهر مستخدم العميل `admin / ADMIN` فقط؛ لم
  يُنشأ `SYSTEM_OWNER` تلقائيًا، وهو متوافق مع حد SEC-OWNER-01 الذي يفصل Owner عن
  Customer Setup وCustomer ADMIN.
- مسار `/system-owner/login` موجود، لكن إنشاء Owner يظل خاضعًا لمسار Commissioning
  الموقع من الشركة ولا يُعامل غياب Owner بعد Pilot Setup كعطل في Customer Admin bootstrap.

هذا التحقق يثبت مسار Pilot Admin/Installer فقط، ولا يغير بوابة قبول Production أدناه.

### 2.3 نقطة التوقف التشغيلية — 19 سبتمبر 2026

- تم تثبيت نسخة الاختبار فعليًا وتشغيل خدمات BIO-EMS الثلاث ونجح HTTPS health.
- تسجيل دخول ADMIN نجح من الواجهة الحالية، لكن تم رصد أن المسار المجرد `/login` قد يعرض shell قديمًا من browser cache؛ المسار cache-busted أظهر الواجهة الحالية. تم إدخال إصلاح revalidation على PR #239 ويجب إعادة اختباره فعليًا دون query string أو hard refresh.
- صفحة `/system-owner/login` الحديثة موجودة، لكن لا يوجد SYSTEM_OWNER قبل Commissioning وهذا سلوك مقصود.
- الخطوة التالية بعد نجاح build الحالي: Commissioning Request -> توقيع Offline بالمفتاح الخاص المشفر -> Import -> MFA QR -> Login -> Audit evidence.
- لا يُسجل أو يُرفع المفتاح الخاص أو عبارة المرور أو كلمة مرور Owner أو TOTP secret/code.

## 3. لماذا لم يتم الدمج بعد

الكود البرمجي مكتمل، لكن قبول Production يحتاج مفتاح الشركة الحقيقي ودورة تشغيل كاملة
به. الدمج قبل ذلك قد يجعل `main` يبدو Production-secure دون إثبات أن المفتاح الحقيقي
والـKeyring والتوقيع Offline يعملون معًا.
