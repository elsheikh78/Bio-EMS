# دليل إتمام الترحيل والشهادة وحماية الـMain

29 أكتوبر 2026. هذه أدوات تنفيذ وليست إثباتًا لتطبيقها على حساب Cloudflare أو أجهزة العميل. الحالة المعتمدة في PROJECT_STATE. المصدر المرشح: Main pilot.9 وTester 0.6.2. كل اختبارات الهاردوير والتأهيل تظل داخل Tester؛ أدوات التصنيع والصيانة التالية لا تمنح قبولًا للهاردوير.

## 1. ترحيل ونشر Cloudflare من PowerShell

من نسخة المشروع المطابقة لطلب الدمج، بوجود Node 22.12 أو أحدث في سلسلة 22 أو Node24، افتح PowerShell عاديًا:

```powershell
.\company-cloud\Invoke-SecurityDeployment.ps1 -Mode inspect -Login
```

أكمل الدخول في متصفح جهازك. الأداة تتحقق من اسم ومعرّف D1 ومن وجود الترحيلين الأساسيين وعدم وجود تاريخ ترحيلات غير معروف. لا ترسل كلمة مرور أو API token في المحادثة. إذا ظهر خطأ هوية أو صلاحيات، لا تختَر قاعدة بديلة بالحدس.

جهز مجلدًا موجودًا خارج مجلد الكود لحفظ النسخ الاحتياطية، ثم:

```powershell
.\company-cloud\Invoke-SecurityDeployment.ps1 -Mode migrate -BackupDirectory 'D:\BIOEMS-Backups'
```

تنشئ الأداة مجلدًا فرعيًا جديدًا بصلاحيات المستخدم وAdministrators وSYSTEM فقط، وتصدر SQL وتحفظ بصمته ونقطة Time Travel قبل تطبيق 0003، ثم تتحقق من الجدول والفهرس والأعمدة وتاريخ الترحيلات. أي فشل يوقف الخطوات اللاحقة. لا تضع ملفات النسخ في Git.

لترحيل ونشر النسخة المطابقة مع بناء الواجهة واختبارات السحابة:

```powershell
.\company-cloud\Invoke-SecurityDeployment.ps1 -Mode deploy -BackupDirectory 'D:\BIOEMS-Backups'
```

احتفظ بملف receipt.json الخاص بالعملية. بعد النشر اختبر الدخول والخروج ورفض الكوكي المنسوخ مع استمرار جلسة أخرى مستقلة؛ النشر الناجح ليس اختبار صلاحيات حيًا. الترحيل الإضافي لا يحذف بيانات العمل. عند تعطل Worker لا تسترجع قاعدة كاملة تلقائيًا فوق كتابات جديدة؛ راجع نقطة الاسترجاع والكتابات اللاحقة. الرجوع إلى Worker القديم ذي الجلسات غير القابلة للإلغاء يحتاج تدوير SESSION_SECRET وفق دليل المرحلة الثانية.

## 2. فحص وتجهيز وتفعيل شهادة Windows

لا تبدّل شهادة سارية تطابق DNS/IP الذي يصل إليه Main. إذا كان رابط IP غير موجود في SAN، اختر عنوانًا ثابتًا/محجوزًا أو DNS فعليًا يمكن للـMain حله، ثم جهز شهادة جديدة بالسكربت New-PlatformTlsCertificate.ps1؛ مسارات PFX/CER جديدة في مجلد محمي، وكلمة مرور عبر Read-Host -AsSecureString. ضمّن الاسم الفعلي وIP الفعلي، وليس عناوين الأمثلة.

التفعيل من PowerShell كمسؤول على كمبيوتر التشغيل، مع استبدال المسارات والرابط ببيانات التثبيت الحقيقية:

```powershell
$password = Read-Host 'Candidate PFX password' -AsSecureString
.\installer\windows\Invoke-PlatformTlsRotation.ps1 `
  -ApplicationRoot 'C:\Program Files\BIOEMS' `
  -PersistentRoot 'C:\ProgramData\BIOEMS' `
  -PlatformUrl 'https://YOUR-STABLE-HOST' `
  -CandidatePfx 'D:\Protected-TLS\next.pfx' `
  -CandidatePassword $password `
  -BackupParent 'D:\BIOEMS-Backups'
```

مسارات الأمثلة ليست اكتشافًا لمسارات جهازك. يلزم تثبيت الباك إند المطابق الذي يحتوي فاحص X509 المترجم. الأداة تتحقق من الشهادة ومفتاحها الخاص، وتنسخ الشهادة القديمة وملف بياناتها، وتوقف Backend وProvisioner، وتحافظ على كلمة مرور الخدمة وملف backend.env وصلاحيات الملفات. تضيف الثقة العامة للشهادة الجديدة على الكمبيوتر، ثم تبدأ الخدمتين وتتحقق عبر TLS من بصمة الشهادة وخدمة health. عند فشل التشغيل تعيد الملفات والبيانات السابقة وتحاول إعادة الخدمات وتسجل حالة الاسترجاع. لا تطبع كلمات المرور.

النجاح يعني تفعيل السيرفر فقط؛ Main القديم قد ينقطع حتى تحديث الثقة العامة المخزنة عليه. نفّذ هذه الخطوة في نافذة صيانة مع اللوحة المتصلة، واحتفظ بسجل الربط وNVS والتخزين. لا تستخدم clearbinding أو erase-flash لتغيير شهادة فقط. لا تحذف ثقة الشهادة القديمة قبل اكتمال التحويل والتحقق من الاسترجاع.

لتحديث ثقة Main مربوط بالفعل بعد تفعيل الشهادة، وصّله بمنفذ USB-UART المعتمد واستخدم `Update-MainTlsTrust.ps1` مع ApplicationRoot وPort وHardwareUid وPublicCertificatePath وPlatformUrl الفعليين. الأداة تفحص الشهادة والسيرفر قبل الاتصال التسلسلي وترفض UID مختلفًا أو جهازًا غير مربوط، ثم تنقل الشهادة العامة والرابط والوقت دون clearbinding أو إعادة pairing. تتحقق من بقاء معرفات الربط كما هي؛ قبولها لا يثبت وصول العينات، فاختبر ذلك في المنصة. للرجوع لشهادة سابقة استخدم نفس الأداة مع ملف CER القديم بعد استرجاع شهادة السيرفر.

للرجوع اليدوي، استخدم مجلد snapshot الناتج والرابط الذي تطابقه الشهادة القديمة:

```powershell
.\installer\windows\Invoke-PlatformTlsRotation.ps1 `
  -ApplicationRoot 'C:\Program Files\BIOEMS' `
  -PersistentRoot 'C:\ProgramData\BIOEMS' `
  -PlatformUrl 'https://PREVIOUS-VERIFIED-HOST' `
  -SnapshotDirectory 'D:\BIOEMS-Backups\tls-EXACT-SNAPSHOT-ID'
```

يتحقق الرجوع من هوية التثبيت وبصمات النسخ ومن أن الشهادة الحالية هي المرشحة المسجلة، ثم يستخدم نفس مسار التفعيل القابل للاسترجاع. شهادة قديمة منتهية أو غير مطابقة للرابط لا تُعتمد كحل أمني. إن سجلت العملية RECOVERY_REQUIRED فحالة الخدمات/الملفات تحتاج فحصًا مباشرًا، ولا تعتبر تلقائيًا مسترجعة.

## 3. التحديث والاسترجاع على لوحة Main

النسخة العادية تبقى Single App ولا تكتب تقسيم A/B تلقائيًا. يوجد بناء منفصل `sdkconfig.maintenance` للوحة اختبار محددة: NVS عند 0x9000، ota_0 عند 0x20000 وota_1 عند 0x210000، سعة كل تطبيق 0x1f0000. تحويل لوحة من التقسيم القديم يتطلب تجهيزًا مباشرًا ونسخة محمية من إعداداتها والتحقق من حجم الفلاش؛ ليس تحديث تطبيق عاديًا. حزمة الصيانة لها manifest مختلف ويرفض مغلف الفيرموير العادي اعتمادها.

على لوحة مؤهلة تحمل ملف A/B فعلًا، وباستخدام USB-UART مناسب لا يعيد تشغيلها عند فتح المنفذ، تتوفر الأوامر `status`, `updatebegin`, `updatechunk`, `updateend`, `updateconfirm`, `updaterollback`, `updateabort`. التحديث يكتب التطبيق غير النشط فقط، يتحقق من SHA256 ومن صورة ESP-IDF والتوقيع إذا Secure Boot مفعل، ثم يعيد التشغيل. أول تشغيل يبقى معلقًا حتى تأكيد صريح، ويعاد تشغيل الجهاز بعد 180 ثانية دون تأكيد ليتراجع bootloader. نجاح النقل لا يؤكد القبول. Baseline أولي لا يملك بديلًا حتى أول تحديث صحيح. اختبره ثم نفذ confirm صريحًا لتسجيله VALID قبل أن تسمح الأداة بنقل أول تحديث؛ حالة BASELINE_UNCONFIRMED لا تسمح ببدء النقل.

أداة النقل تحتاج Python وpyserial على محطة الصيانة:

```powershell
python .\tools\device-security\usb_update.py --port COM5 --uid EXACT_HARDWARE_UID --action inspect
python .\tools\device-security\usb_update.py --port COM5 --uid EXACT_HARDWARE_UID --action stage --image app.bin --sha256 GOVERNED_SHA256
python .\tools\device-security\usb_update.py --port COM5 --uid EXACT_HARDWARE_UID --action confirm --accept-functional-checks
```

استبدل UID وSHA256 من سجل اللوحة وحزمة الإصدار المعتمدة. لا تستخرج SHA من ملف مجهول وتعتبر ذلك توقيع ناشر. تحقق قبل التأكيد من الهوية والشبكة والعينات والوقت والتخزين. بعد فشل التحديث يجب التحقق من رجوع النسخة السابقة مع إعداداتها وبياناتها. جرّب فصل الطاقة أثناء النقل وأول تشغيل على اللوحة المخصصة، وتحقق من رفض الصورة التالفة/الموقعة بمفتاح آخر على جهاز محمي. بعض منافذ USB تتغير أو تتوقف بعد تفعيل الحماية؛ اعتماد منفذ الاسترجاع جزء من الاختبار الفعلي.

## 4. المفاتيح وتفعيل الإنتاج

يمكن تجهيز مفتاح توقيع RSA3072 على كمبيوتر المالك، خارج المصدر وفي مجلد موجود محمي:

```powershell
.\tools\device-security\New-MainSigningKey.ps1 -KeyParent 'D:\Offline-Keys' -Owner 'ACTUAL-KEY-OWNER'
```

لا ينشئ هذا مفتاح فلاش مشتركًا ولا يغير جهازًا. PEM الخاص غير مشفر لتوافق أدوات ESP-IDF؛ صلاحيات المجلد وحدها لا تغني عن قرص مشفر ونسخة احتياطية مشفرة منفصلة واختبار استعادتها. inventoryId معرف جرد فقط، وليس بصمة eFuse. استخدم ESP-IDF/espsecure لحساب بصمة Secure Boot وتوقيع bootloader/app؛ لا تحرق hash ملف PEM داخل الشريحة.

قبل تفعيل أي eFuse: سجّل UID ومراجعة الشريحة والفلاش، افحص إعدادات الحماية الحالية مستقلًا، اختبر بناء A/B والتوقيع والاسترجاع على لوحة مخصصة، اعتمد مالك المفتاح وطريقة نسخ مفتاح التوقيع وتدويره، وحدد سياسة مفتاح تشفير مختلف لكل جهاز ومنفذ التحديث بعد القفل. لو ولّد الجهاز مفتاحًا غير قابل للقراءة فلا تعد باسترجاع نسخة منه لاحقًا. اختبر مسار التحديث الموقع واحتفظ بلوحة بديلة عند تلف مسار إقلاع مقفول.

لا تحتوي الأدوات على أوامر حرق eFuse أو تفعيل تلقائي. Secure Boot/Flash Encryption/NVS encryption وإغلاق debug/download تحتاج ملف تصنيع محددًا ومراجعة على الأجهزة، ولا يثبتها نجاح build. بوابة sdkconfig.production-gate تفحص الحماية المفعلة أصلًا فقط. PKI/mTLS وهوية المفاتيح لكل جهاز وإلغاء الشهادات ما زالت مسارًا إنتاجيًا مستقلًا غير مكتمل؛ لا يساويها نجاح pairing أو HTTPS. حماية Nano الكلاسيك تحتاج معالجة منفصلة ولا تُعتمد بتفعيل حماية Main.
